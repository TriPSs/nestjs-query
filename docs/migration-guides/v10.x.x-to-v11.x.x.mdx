title: 'v10.x.x to v11.x.x'

---

In v11, the default `maxResultsSize` is `100` for both GraphQL and REST, up from `50` in v10. This affects endpoints that use the generated paging arguments without an explicit maximum.

## What changes

GraphQL offset queries accept a `limit` up to `100`, cursor queries accept `first` or `last` up to `100`, and REST offset queries accept a `limit` up to `100`. With request validation enabled, requests for 51–100 records that previously failed validation are now accepted. Requests above `100` still fail validation unless you configure a higher maximum.

The default number of records returned when a client omits the page size remains `10` for GraphQL and `25` for REST. Existing `maxResultsSize` overrides continue to apply. CSV exports use their separate `limit` option.

## Adopt the new maximum

No configuration change is required to use the new maximum. Update any client-side page-size validation or tests that assume requests above `50` are rejected. REST's generated OpenAPI paging metadata also advertises a maximum of `100`.

## Keep the previous maximum

Set `maxResultsSize: 50` on each DTO whose endpoints should retain the previous limit.

### GraphQL

```ts
import { ObjectType } from '@nestjs/graphql'
import { FilterableField, QueryOptions } from '@ptc-org/nestjs-query-graphql'

@ObjectType('TodoItem')
@QueryOptions({ maxResultsSize: 50 })
export class TodoItemDTO {
  @FilterableField()
  title!: string
}
```

### REST

```ts
import { FilterableField, QueryOptions } from '@ptc-org/nestjs-query-rest'

@QueryOptions({ maxResultsSize: 50 })
export class TodoItemDTO {
  @FilterableField()
  title!: string
}
```

Check endpoint-level query options as well: explicit resolver or controller settings override the DTO defaults. Set any applicable `maxResultsSize` override to `50` to keep that endpoint's previous maximum.

See [GraphQL query options](/graphql/dtos#queryoptions) and [REST paging](/rest/queries/paging) for further configuration.

## REST CSV boolean serialization

In v11, REST CSV exports serialize boolean values as the unquoted literals `true` and `false`. In v10, they emitted `1` for `true` and an empty field for `false`.

## CSV export dependency

CSV export now loads `csv-stringify` only when an export endpoint is called. Applications that use CSV export must install it explicitly:

```sh
npm install csv-stringify
```

Applications that do not use CSV export can omit it.

## REST Swagger runtime dependency

`@ptc-org/nestjs-query-rest` requires `@nestjs/swagger` at runtime, even when an application does not generate OpenAPI documentation. Its `@ApiProperty` decorators run when REST DTO classes are defined, so the dependency cannot be loaded lazily. Keep `@nestjs/swagger` installed when upgrading.

## Relation filter aliases

If you subclass `FilterQueryBuilder` and override `applyFilter`, accept and forward its new optional fourth argument. An override that drops it recomputes the relation alias map and can qualify a filter with the wrong relation's alias.

Otherwise no action is required. Queries where a selected relation shared a name with a filtered one previously returned the wrong rows and now return the right ones.

## Custom builders on relation paths

In v10, a builder configured through `TypeOrmQueryServiceOpts.filterQueryBuilder` was replaced by a default builder wherever a query reached a relation. In v11 it also applies to filters that descend into a relation, to selected relations, to `queryRelations`, `countRelations`, `aggregateRelations` and `findRelation`, single and batch, and to the lookups `addRelations`, `setRelations`, `setRelation`, `removeRelations` and `removeRelation` make. Expect different SQL and results on those paths. For example, a builder that scopes queries to a tenant now also limits which relations those five methods can find, so they throw `Unable to find ...` for a relation outside the tenant.

A `FilterQueryBuilder` subclass that overrides `applyFilter` is now also called for relation queries. For a selected relation it is called on a builder copied for the relation rather than on the root builder, so `this.repo` is the relation's repository.

### Subclasses that need a change

Each builder is copied for the relation, through `deriveForEntityMetadata` on `SQLComparisonBuilder` and `WhereBuilder`, and `deriveForRepository` on `AggregateBuilder` and `FilterQueryBuilder`. The copy is shallow and keeps the prototype, which breaks three subclass shapes:

- A subclass holding ECMAScript `#private` fields raises a `TypeError` wherever the copy reads one. For a `FilterQueryBuilder` subclass that can be any relation query or selected relation, and for an `AggregateBuilder` subclass any relation aggregate.
- A subclass that computes state from `entityMetadata` or `repo` silently uses the root entity's state for the relation. That covers state computed in the constructor, and state cached in an own object such as a `Map`, which the copy shares with the root builder in both directions.
- A subclass whose methods are arrow function class fields, or are bound in its constructor, keeps `this` pointing at the root builder in those methods.

Fix each by overriding the matching `deriveFor...` method to construct the copy yourself. TypeScript's `private` keyword is unaffected. An overriding `FilterQueryBuilder` also has to derive its where and aggregate builders, or relation queries fall back to default ones:

```ts
class TenantFilterQueryBuilder<Entity> extends FilterQueryBuilder<Entity> {
  public deriveForRepository<Relation>(repo: Repository<Relation>): FilterQueryBuilder<Relation> {
    return new TenantFilterQueryBuilder<Relation>(
      repo,
      this.whereBuilder.deriveForEntityMetadata<Relation>(repo.metadata),
      this.aggregateBuilder.deriveForRepository<Relation>(repo)
    )
  }
}
```

### `SQLComparisonBuilder.forEntityMetadata` removed

The public static `SQLComparisonBuilder.forEntityMetadata`, shipped in `11.0.0-alpha.0` and `11.0.0-alpha.1`, is removed. Replace `SQLComparisonBuilder.forEntityMetadata(metadata)` with `new SQLComparisonBuilder(SQLComparisonBuilder.DEFAULT_COMPARISON_MAP, undefined, metadata)`, or keep a builder's behaviour with `builder.deriveForEntityMetadata(metadata)`.
