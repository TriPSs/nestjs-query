title: 'v10.x.x to v11.x.x'
description: 'Migrate query limits, CSV exports, and REST Swagger dependencies.'
---

In v11, the default `maxResultsSize` is `100` for both GraphQL and REST, up from `50` in v10. This affects endpoints that use the generated paging arguments without an explicit maximum.

## What changes

GraphQL offset queries accept a `limit` up to `100`, cursor queries accept `first` or `last` up to `100`, and REST offset queries accept a `limit` up to `100`. With request validation enabled, requests for 51–100 records that previously failed validation are now accepted. Requests above `100` still fail validation unless you configure a higher maximum.

The default number of records returned when a client omits the page size remains `10` for GraphQL and `25` for REST. Existing `maxResultsSize` overrides continue to apply. CSV exports use their separate `limit` option.

## Adopt the new maximum

No configuration change is required to use the new maximum. Update any client-side page-size validation or tests that assume requests above `50` are rejected. REST's generated OpenAPI paging metadata also advertises a maximum of `100`.

## Keep the previous maximum

Set `maxResultsSize: 50` on each DTO whose endpoints should retain the previous limit.

### GraphQL

```ts
import { ObjectType } from '@nestjs/graphql'
import { FilterableField, QueryOptions } from '@ptc-org/nestjs-query-graphql'

@ObjectType('TodoItem')
@QueryOptions({ maxResultsSize: 50 })
export class TodoItemDTO {
  @FilterableField()
  title!: string
}
```

### REST

```ts
import { FilterableField, QueryOptions } from '@ptc-org/nestjs-query-rest'

@QueryOptions({ maxResultsSize: 50 })
export class TodoItemDTO {
  @FilterableField()
  title!: string
}
```

Check endpoint-level query options as well: explicit resolver or controller settings override the DTO defaults. Set any applicable `maxResultsSize` override to `50` to keep that endpoint's previous maximum.

See [GraphQL query options](/graphql/dtos#queryoptions) and [REST paging](/rest/queries/paging) for further configuration.

## REST CSV boolean serialization

In v11, REST CSV exports serialize boolean values as the unquoted literals `true` and `false`. In v10, they emitted `1` for `true` and an empty field for `false`.

## CSV export dependency

CSV export now loads `csv-stringify` only when an export endpoint is called. Applications that use CSV export must install it explicitly:

```sh
npm install csv-stringify
```

Applications that do not use CSV export can omit it.

## REST Swagger runtime dependency

`@ptc-org/nestjs-query-rest` requires `@nestjs/swagger` at runtime, even when an application does not generate OpenAPI documentation. Its `@ApiProperty` decorators run when REST DTO classes are defined, so the dependency cannot be loaded lazily. Keep `@nestjs/swagger` installed when upgrading.

## Malformed filters are rejected

In v11, a filter that cannot be read as either a comparison or a nested filter raises an `InvalidFilterError` rather than being evaluated to a result. These shapes are affected:

- nesting into a field that holds a value rather than an object, for example `{ role: { nin: { neq: 'admin' } } }` where `role` holds a string and `nin` is not an operator. A field that holds a `Date` or an array is treated the same way,
- mixing recognised comparison operators with keys that are not operators, for example `{ role: { eq: 'admin', tenant: 'acme' } }`,
- giving an operator an object literal or an array as its value, for example `{ role: { neq: { eq: 'admin' } } }`, `{ role: { neq: {} } }` or `{ role: { eq: ['admin'] } }`. A `Date` or a class instance is still accepted,
- giving `in` or `notIn` a value that is not an array, or an array that holds an object literal or another array, for example `{ role: { in: 'admin' } }` or `{ role: { notIn: [blockedRoles] } }`,
- giving `like`, `notLike`, `iLike` or `notILike` a value that is not a string, or `between` or `notBetween` a value without both a `lower` and an `upper` key, including `null`,
- giving a field a value that is not an object at all, for example `{ ownerId: 42 }`, `{ ownerId: null }` or `{ createdAt: new Date() }`.

These shapes were evaluated in v10, and the result was unreliable rather than merely wrong. The first read the unrecognised key as a relation name, compared `undefined` against the value, and for the negative operators (`neq`, `is`, `isNot`, `notLike`, `notILike`, `notIn`) returned a match. The third compared the field against an object, so `neq` and `isNot` always matched, and so did `gt` and `gte` for most strings. The fourth matched `in` against a substring of the string it was given, and `notIn` of a nested array always matched. The fifth raised a `TypeError`, or for a missing bound compared the field against `undefined`. The sixth never matched most numbers and booleans, a `Date` or an array, and raised a `TypeError` for `null`. Where such a filter was an authorization filter enforced on creation, a record was permitted that the filter was written to reject. The second reported the wrong key, naming the operator that was correct rather than the one that was not.

The first shape can only be detected from the record being evaluated. Core has no DTO metadata, so `{ role: { nin: { neq: 'admin' } } }` has the same shape as a filter on a relation `role` with a field `nin`. When the record holds `null` or `undefined` for `role`, which is what a create input that omits the field produces, the filter is still read as a filter on an absent relation, and its negative operators still match. The client chooses what a create input contains, so a client that omits the field still passes such a filter, and the error only reaches callers that supply it. It is a way to find the mistake, not a defence against it. Correct the filter rather than relying on the error.

No action is required for filters that are already well formed, and filters sent through the GraphQL API were never affected because the generated input types reject unknown keys before they are evaluated. Filters written in code are worth checking, authorization filters first, since those are the ones evaluated in memory.

`InvalidFilterError` is not an HTTP exception, so a malformed filter surfaces as a server error rather than a `400`. That is deliberate: the GraphQL and REST layers reject unknown filter keys against their generated input types, so a filter that reaches evaluation malformed was written in server code, and reporting it as a client error hides the fault. `BadRequestException` keeps its existing meaning, that a record failed a filter that was evaluated successfully. A boundary that does accept filters written by a client can catch `InvalidFilterError` and rethrow whatever suits it.

This changes what a client sees when an authorization filter enforced on creation is malformed. Where v10 happened to evaluate it to no match, `createOne` answered `400 Entity does not meet creation constraints` over REST and a `BAD_REQUEST` error over GraphQL, and `createMany` silently dropped the records. v11 answers `500` over REST and an `INTERNAL_SERVER_ERROR` over GraphQL for both. Every filter that core cannot read now raises `InvalidFilterError`, including the `unknown comparison` and `unknown operator` errors that were a plain `Error` in v10. Its message is unchanged and it is still an `Error`, so existing handlers keep working. The messages name the field, the operator and the offending keys, but not the values the filter compares against. GraphQL returns the message of an `INTERNAL_SERVER_ERROR` to the client even in production, where only the stack trace is removed, so a malformed authorization filter shows the client those names.

`and` and `or` are grouping keys rather than fields or operators, so a filter that combines a group with a field named after an operator, such as `{ owner: { and: [...], is: { eq: true } } }`, is unaffected. So is a nested filter that combines such a field with another field, such as `{ owner: { is: { eq: true }, name: { eq: 'a' } } }`. A nested filter whose keys are all fields named after operators, such as `{ owner: { is: { eq: true } } }`, reads as a comparison of `owner` itself. It never matched in v10 and is rejected in v11. Wrap it in `and`, as in `{ owner: { and: [{ is: { eq: true } }] } }`, to filter on the field.
